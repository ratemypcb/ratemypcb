# Phase 5 Research: Manufacturing Evidence Model and Gerber Baseline

**Researched:** 2026-08-27  
**Confidence:** High for current code seams, Ucamco format/corpus boundaries, dependency hazards, and the model direction; medium for final `gerber_parser` adoption until the mandatory checkpoint passes.

## Research summary

The current Rust fabrication path does not parse Gerber or Excellon semantics. It loads bounded UTF-8 strings, recognizes roles from filenames, checks a few required tokens, and can mark required fabrication coverage passed. The browser has a substantially deeper Gerber renderer, but it is a presentation-only `f64` parser with a deliberately different supported subset and cannot become report evidence.

The shortest safe Phase 5 path is:

1. establish the canonical model/capability contract and immediately downgrade legacy screening;
2. conditionally adopt `gerber_parser` 0.5.0 behind a byte/resource/error-accounting boundary and interpret supported Gerber/X2 commands into fixed-point canonical geometry;
3. add a strict XNC parser, Gerber Job/package analysis, native KiCad reconciliation, and complete product/report gates.

No new framework is needed. One `fabrication.rs` module, the existing `review()`/evidence/schema seams, the Rust test harness, and Node's existing contract tests are sufficient.

## Current code findings

### Input and package seams

- `classify`, `collect_dir`, `load_path`, and `load_zip` recognize Gerber and drill extensions. They do not recognize Gerber Job files.
- `Loaded.manufacturing` stores `(path, kind, String)`. Invalid UTF-8 is rejected globally, oversized manufacturing files are silently omitted, and per-artifact digests/omissions are not retained. Phase 5 needs original bytes, typed load outcomes, and exact per-file digest/provenance.
- The archive boundary already rejects unsafe and duplicate normalized paths and bounds compressed/expanded bytes and entries. Gerber Job references should resolve only against this virtual inventory; no extraction to shared OS paths is needed.
- ZIP package coverage currently infers top/bottom/profile from filenames and can call that complete before semantic parsing.

### Fabrication policy seams

- `gerber_syntax_valid` checks `M02`, `%MO`, `%FS`, and aperture presence when draw-like lines exist. It is token screening, not a parser.
- `manufacturing_review` checks filename roles, mask filename pairs, and whether drill text contains unit/tool/coordinate tokens. It can emit `Passed` for `gerber-syntax` and `drill-data` without semantic coverage.
- `required_coverage` already requires `package-gerbers`, `gerber-syntax`, and `drill-data` for fabrication/assembly/full reviews. These IDs should remain stable while their authority changes from partial screening to semantic capabilities.
- `finalize_evidence`, `required_evidence_summary`, `approval_eligible`, and `validate_report` are the Phase 1 integration points. Manufacturing records must supply exact per-artifact/canonical digests and structured locations before those helpers create public evidence IDs.
- `Stackup::from_gerbers` counts copper-looking filenames. It is useful only as weak inventory inference and must not remain canonical construction evidence.

### Native source and presentation seams

- `BoardFacts` and `parse_board` contain basic KiCad source facts, but no canonical layer/profile/drill/extent/connectivity adapter. Phase 5 should emit native manufacturing facts into the same model rather than promote `BoardFacts` or parse the browser model.
- Phase 4's `schematic` implementation demonstrates bounded parsing, artifact composites, source-pair provenance, evidence-only gate validation, and fixture manifests. Reuse those patterns, not the schematic data model.
- `board-view.js::parseGerber`, `classifyGerberLayer`, and `inspectGerberSet` support useful visualization and coarse inventory but use `f64`, browser-only resource logic, assumptions, and a different subset. `local-viewer.js` must consume core fabrication evidence separately. Browser parsing remains non-authoritative.
- The report schema is hand-generated by `report_schema()` and equality-tested against `schemas/report-2.0.json`. Additive Phase 5 fields must preserve that authority.

## Official baseline and legal boundary

Ucamco currently publishes:

- Gerber Layer Format revision 2026.05;
- PEG/EBNF grammar;
- Gerber Job JSON Schema revision 2023.06;
- XNC revision 2021.11;
- fabrication and XNC test corpora from its downloads page.

Revision 2026.05 describes typo/error/text corrections from 2024.05 rather than a format-language change. A parser targeting 2024.05 can be tested against 2026.05, but RateMyPCB must state the exact tested subset/corpus and cannot claim blanket conformance from acceptance alone.

The specification copyright text does not grant redistribution merely because the files are publicly downloadable. Official PDFs, schemas, ZIPs, and extracted files remain local-only checkpoint inputs unless explicit redistribution permission is obtained. Repository fixtures must be project-authored or demonstrably redistribution-safe and include a manifest with origin, license, sanitization, expected capability, and SHA-256.

## Dependency research

### `gerber_parser` 0.5.0 — conditional only

- License: MIT OR Apache-2.0.
- Maintainer/project: MakerPnP; describes itself as mature and targets Gerber 2024.05.
- Modeled features include apertures/macros, interpolation/arcs, regions, polarity/transforms, blocks, step-repeat, file/aperture/object attributes, standard attributes, and deprecated commands.
- It has no application resource limits. RateMyPCB must pre-bound bytes/records/text/numbers and guard macro/block/step-repeat interpretation and canonical output itself.
- It reads UTF-8 lines. Official files contain CP-1252 en dashes in human `G04` comments. Invalid bytes can be normalized only through D-07's non-semantic comment boundary, with original digest and warning retained.
- `GerberDoc::commands()` and `into_commands()` filter per-command failures. Production code must collect and classify every `errors()` item before consuming commands. Zero unaccounted errors is a hard invariant.
- After bounded non-semantic-comment normalization, the readiness spike parsed 31 of 32 official Gerber files and 102,909 commands. The remaining valid route layer exposed `%TF.FileFunction,NonPlated,1,4,NPTH,Route*%` as an unsupported standard attribute. Adoption requires an upstream correction or the exact semantic adapter in D-08.
- Geometry interpretation, fixed-point conversion, modal state, transforms, expansion bounds, semantic completeness, and canonical digests remain RateMyPCB responsibilities.

The dependency checkpoint must inspect the exact locked dependency tree, license files, security advisories available in the existing toolchain, API/error behavior, route record, local official corpus, and project-authored hostile corpus. To make that evidence executable, first pin `gerber_parser = "=0.5.0"` only in core `[dev-dependencies]`, allow `Cargo.lock` to record the candidate graph, and compile the bounded spike harness with `--locked`; production source must not import it. Dev/spike lock inclusion is not production adoption. A `blocking-human` gate chooses PASS, which promotes the same exact version to normal workspace/core dependencies before adapter work, or STOP, which removes the spike pin/candidate-only lock entries and stops 05-02 for replanning. STOP does not silently switch dependencies or bless the token checker, and an independent AI review cannot substitute for the human checkpoint decision.

### `gerberx2` 0.1.2 — local oracle only

The readiness spike observed 32/32 official Gerber files after the same comment normalization, 102,909 commands, and 83,570 objects. It is nevertheless unsuitable as a production dependency: it is new, uses `f64`, reads whole sources, expands step-repeat without product budgets, and pulls rendering/font/image/SVG/overlay dependencies through `pcb-ir`. It may be invoked locally on sanitized or official local-only data as a differential oracle. It must not appear in workspace/core Cargo manifests, `Cargo.lock`, production code, CI downloads, or release artifacts.

## Canonical manufacturing model

### Document and package identity

`FabricationReview` contains a deterministic package ID/model digest, product/job identity, source documents, capabilities, omissions, conflicts, package checks, and reconciliations. Each document retains normalized virtual path, original-byte SHA-256, adapter/spec version, parse status, warnings, and structural source locations.

Stable IDs use version-tagged tuples:

- document: original artifact digest + format;
- layer/tool/feature: document ID + canonical semantic kind + structural command/record location + parent identity;
- package: sorted document IDs + authoritative product/job identity;
- canonical digest: deterministic serialization of sorted semantic records, capabilities, omissions, and conflicts, excluding prose diagnostics, wall-clock time, local paths, and package enumeration order.

Duplicate identities and digest disagreement fail validation.

### Fixed point and transforms

- Canonical length is signed `i64` picometres.
- Decimal lexemes are parsed as sign/mantissa/scale with checked `i128` intermediates, then converted exactly from mm/inch. Maximum accepted decimal scale is 9 and maximum physical extent is ±10 m.
- Each document records source unit, format, and resolution; each feature can trace the source numeric lexeme/location.
- Ordered transforms preserve mirror, fixed microdegree rotation, and rational scale without `f64`. Right-angle transforms materialize exactly. Any other materialization uses one specified deterministic fixed-point routine, checked overflow, and an explicit maximum error/quantization record; capability is partial if that contract cannot be met.
- Arcs retain exact start/end/center or offset, direction, quadrant mode, and resolution. They are not flattened into display chords in production evidence.
- Step-repeat and aperture blocks retain definitions and bounded instances; no analyzer can demand expanded geometry unless the `geometry.expanded` capability is complete.

### Capabilities, omissions, and analyzers

A capability record distinguishes `complete`, `partial`, `not_provided`, `unsupported`, and `failed`, with evidence source, authority, prerequisite IDs, and detail. Omissions identify the exact record/range and capability impact. Conflicts retain both facts and their authorities.

Adapters only parse and normalize. Package/reconciliation analyzers declare prerequisite capability IDs. The analyzer dispatcher emits `not_checked` whenever any prerequisite is not `complete`; it never treats a format badge or warning-free parse as evidence.

Minimum capability families cover product identity, layers/roles/order, units/format, geometry primitives, arcs, regions, polarity, transforms, repetition, apertures/macros, profile, extents, drills/routes/slots/tools/plating/spans, X2/Job attributes, net/component/pin semantics, construction, native KiCad facts, and package reconciliation.

## Gerber production boundary

The byte preflight:

1. enforces raw/aggregate/deadline budgets and records original SHA-256;
2. lexes ASCII syntax boundaries without decoding semantic text;
3. rejects invalid bytes outside a complete `G04...*` command or inside `G04 #@!`, extended commands, attributes, names, or numeric syntax;
4. replaces invalid runs only in an ordinary human G04 payload in a parser-only copy and records original byte spans/counts;
5. rejects unterminated/ambiguous comments and all prohibited control bytes.

After dependency parsing, the wrapper inspects every parser error. Only the exact route FileFunction compatibility result can be resolved locally, and only after the raw record validates and its full semantic fields are retained. Every other error fails the affected semantic capabilities. Unsupported commands/attributes discovered during interpretation are omissions/failures, never skipped.

The interpreter must prove modal coordinate/aperture/operation/interpolation/quadrant state; units/format; flashes/draws/arcs; regions/contours; polarity; aperture macros/blocks; mirror/rotation/scale; step-repeat; terminal M02; and data-after-terminator behavior under the declared budgets.

## XNC / Excellon direction

Ucamco XNC 2021.11 is a compact strict subset of IPC-NC-349. It uses explicit decimal coordinates, `METRIC`/`INCH`, tools T01..T99 with finished diameters, drill hits, linear/CW/CCW route segments, M30 termination, and Gerber-style attributes for plating, layer span, and drill function.

A dedicated bounded stdlib state machine is smaller and safer than another dependency. It maintains explicit header/body, unit, absolute-coordinate, current tool, position, drill/route, interpolation, plating, and layer-span state. Missing units/decimal placement/tool/modal position/terminator, undefined tools, unclosed routes, data after M30, unsupported commands, and numeric/record/deadline breaches fail closed.

Official XNC samples include exporter extensions such as `FMAT,2`, `G90`, `M71`, `T0`, and `METRIC,TZ`. These are not a generic permissive mode. Fixture manifests define separate `strict-xnc`, `kicad-legacy-excellon`, and `librepcb-legacy-excellon` profiles with exact generator signatures and command allowlists. Unknown exporters or commands remain unsupported. Missing plating is unknown, not non-plated; missing layer span remains unknown.

## Gerber Job, package completeness, and reconciliation

Recognize `.gbrjob`/declared Gerber Job JSON under byte, token, nesting, collection, path, and deadline limits. Validate the supported 2023.06 shape and resolve every referenced path against the existing virtual inventory. Missing, duplicate, external, case/Unicode-conflicting, or wrong-digest/type references are conflicts/failures.

Authority is explicit: valid X2 file facts and valid Job facts are stronger than filename inference; disagreement remains a conflict. Filename grouping is only a partial fallback. Package completeness considers intended product identity, unique layer roles/order, one profile with cutouts, drill/rout coverage and plating/span state, compatible extents/resolution, and connectivity only when X2 object coverage is complete.

The native KiCad adapter emits only explicit board facts needed for reconciliation: product/revision identity, copper/layer roles, Edge.Cuts/profile topology and extent, via/pad drill or slot facts, and net/pad connectivity. It does not add DFM thresholds. Reconciliation compares exact facts or resolution-derived equality only; no Phase 7 clearance/tolerance policy is introduced. Missing capability produces not checked; mismatch preserves both source and package evidence.

## Validation architecture

1. **Model contract tests:** fixed conversion/overflow, transform snapshots, stable IDs/digests, capability prerequisite truth table, omission/conflict validation, and legacy-screening downgrade.
2. **Gerber adapter tests:** byte normalization, every parser error accounted, exact route attribute, modal semantics, all required geometry constructs, fixed point, X2 completeness, resource/deadline failures, and deterministic output.
3. **XNC/Job/package tests:** strict and named legacy dialects, tools/plating/spans/routes/slots, Job path authority, package grouping/completeness, and native/package mismatch matrix.
4. **Corpus/security tests:** project-authored sanitized positives/hard negatives/mutations in normal CI; official Ucamco archives only through a required local adoption/closure checkpoint; optional local differential oracle with no customer upload.
5. **Vertical gates:** report/schema equality, CLI digest/render tracer, viewer policy neutrality, skill/docs agreement, full Rust/Node/fmt/clippy/diff gates, and fresh independent review.

## Residual risks

- `gerber_parser` adoption is intentionally unresolved until 05-02's checkpoint; plans do not pretend the current spike is approval.
- The advertised 2026 layer corpus remains unavailable. Passing older official corpora and sanitized fixtures cannot erase that gap.
- Official Ucamco assets remain local-only; CI cannot claim official-corpus execution.
- Package connectivity is often absent or partial in real X2 output. The model must preserve that absence even if all geometry parses.
- Native KiCad/package reconciliation validates equality and completeness prerequisites only. Fabricator-specific geometric acceptability remains Phase 7.
